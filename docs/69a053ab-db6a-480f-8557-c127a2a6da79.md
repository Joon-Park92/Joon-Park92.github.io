### PromQL 기초 문법 정리

## TL;DR

- PromQL은 Prometheus에서 시계열 데이터를 조회하는 쿼리 언어임.
- 기본적인 쿼리 패턴으로 인스턴스 상태 조회, 레이블 필터링, 집계 함수 등을 제공함.
- `rate()`, `sum()`, `avg()`, `increase()` 등의 집계 및 함수 활용이 중요함.

## 기본 문법

- `{}` 중괄호를 사용해 특정 메트릭을 필터링할 수 있음.
- `metric_name{label="value"}` 형태로 레이블을 지정하여 원하는 데이터만 조회 가능함.
- `rate(metric[5m])`처럼 시간 기반 함수 사용 가능.

~~~promql
# CPU 사용량 조회
node_cpu_seconds_total{mode="idle"}
~~~

## 레이블 필터링

- `=` : 특정 값과 일치하는 레이블 선택.
- `!=` : 특정 값과 일치하지 않는 레이블 선택.
- `=~` : 정규 표현식 사용 가능.
- `!~` : 정규 표현식과 일치하지 않는 레이블 선택.

~~~promql
# 특정 인스턴스의 메모리 사용량 조회
node_memory_Active_bytes{instance="server1:9100"}

# 특정 모드를 제외한 CPU 사용량 조회
node_cpu_seconds_total{mode!="idle"}
~~~

## 집계 함수 활용

- `sum()`: 전체 합을 구함.
- `avg()`: 평균을 계산함.
- `min()`, `max()`: 최소/최대값을 찾음.
- `count()`: 데이터 개수를 셈.

~~~promql
# 모든 노드의 CPU 사용량 합계
sum(node_cpu_seconds_total)

# 특정 모드를 제외한 평균 CPU 사용량
avg(node_cpu_seconds_total{mode!="idle"})
~~~

## 시간 기반 함수

- `rate(metric[5m])`: 5분 동안의 평균 증가율을 계산.
- `increase(metric[1h])`: 1시간 동안 증가한 값 계산.
- `irate(metric[1m])`: 1분 동안의 순간 증가율 계산.

~~~promql
# 5분 간 평균 HTTP 요청 속도
rate(http_requests_total[5m])

# 1시간 동안 증가한 네트워크 수신 바이트(counter)
increase(node_network_receive_bytes_total[1h])
~~~

## 비교 연산자와 조건

- `>` : 크다, `<` : 작다, `>=` : 크거나 같다, `<=` : 작거나 같다.
- `==` : 같음, `!=` : 다름.
- `and`, `or`, `unless` 등의 논리 연산 사용 가능.

~~~promql
# CPU 사용량이 80% 이상인 인스턴스 찾기
node_cpu_seconds_total / node_cpu_seconds_total{mode="idle"} > 0.8
~~~

## 조인과 그룹화

- `on(label)`: 특정 레이블 기준으로 조인.
- `group_left`, `group_right`를 사용하여 레이블 개수를 맞출 수 있음.

~~~promql
# HTTP 요청 수 대비 에러 비율 계산
sum(rate(http_requests_total{status="500"}[5m]))
/
sum(rate(http_requests_total[5m]))
~~~

## 마무리

- PromQL은 Prometheus 환경에서 데이터를 분석하는 필수 도구임.
- 기본 문법과 함수들을 조합하여 원하는 데이터를 쉽게 조회할 수 있음.
- 실전에서는 Grafana와 함께 사용하면 시각화를 통해 더욱 직관적으로 데이터를 분석 가능함.

## Hermes 실습용 PromQL 문법 — 결과 타입부터 읽는다

> [!info] 공식 문서
> - [Prometheus querying basics](https://prometheus.io/docs/prometheus/latest/querying/basics/) · [operators](https://prometheus.io/docs/prometheus/latest/querying/operators/) · [functions](https://prometheus.io/docs/prometheus/latest/querying/functions/)

1. **PromQL 결과는 값 하나가 아니라 시계열 집합이다**
    - **instant vector** = 현재 시각의 `metric{label="value"}` 시계열 집합이다.

    ```promql
    airflow_ti_finish{state="failed"}
    ```

    - **range vector** = 각 시계열의 시간 창 표본 집합이다. `[5m]`이 range selector다.

    ```promql
    airflow_ti_finish{state="failed"}[5m]
    ```

    - **scalar** = 숫자 하나다. 집계나 함수가 vector를 scalar로 바꿀 수 있다.
    - **empty vector** = metric·label 조합이 없거나 함수가 계산할 표본을 충분히 못 찾은 결과다. `0`과 다르다.

2. **selector — 어떤 시계열을 읽을지 고른다**
    - `=` / `!=`는 정확 일치·불일치, `=~` / `!~`는 RE2 정규식 일치·불일치다.

    ```promql
    # 정확한 Airflow task failure series
    airflow_ti_finish{
      dag_id="observability_metric_alert_drill",
      task_id="emit_marker_and_fail",
      state="failed"
    }

    # scheduler 또는 web container의 로그와 같은 namespace를 보는 metric
    up{namespace="airflow", job=~"airflow-.*"}
    ```

    - label selector는 **낮은 cardinality 탐색 축**에만 쓴다. `dag_id`·`task_id`·`state`는 적합하지만 request ID·사용자 ID·전체 오류 문자열은 metric label로 만들지 않는다. [[2026-07-01 - Prometheus 메트릭 데이터 모델·라벨·cardinality·StatsD 매핑 (hermes airflow-metrics 실측)#4. cardinality 폭발 — hermes 실측 (핵심 교훈)|cardinality 실측]].

3. **range 함수 — counter와 gauge를 구분한다**
    - counter는 누적값이므로 `rate` 또는 `increase`로 시간 창의 변화를 읽는다.

    ```promql
    # 초당 실패율
    rate(airflow_ti_finish{state="failed"}[5m])

    # 5분 동안 늘어난 실패 수
    increase(airflow_ti_finish{state="failed"}[5m])
    ```

    - gauge는 현재값 자체나 `avg_over_time`·`max_over_time`처럼 창 내부의 상태를 본다.

    ```promql
    # 5분 동안 가장 높았던 memory working set
    max_over_time(container_memory_working_set_bytes{namespace="airflow"}[5m])
    ```

    - **첫 표본 함정**: 새 counter series가 처음 `1`로 수집되면 이전 표본이 없어 `increase(...[5m])`가 empty vector가 될 수 있다.
        - 2026-07-14 drill에서 `airflow_ti_finish{dag_id="observability_metric_alert_drill",state="failed"} = 1`은 존재했지만 첫 표본이라 `increase` 결과는 비었다.
        - 일회성 drill rule은 `metric > 0`으로 평가하고, 일반 운영 counter alert는 충분한 scrape history·window·reset 동작을 고려해 `rate`/`increase`를 택한다. 실습 상태 → [[2026-07-13 - hermes-observability - 01 metric alert log drill#작업 진행 노트|metric alert log drill]].

4. **집계 — 무엇을 버리고 무엇을 남길지 명시한다**

    ```promql
    # 모든 실패 task를 DAG별로 합산
    sum by (dag_id) (
      rate(airflow_ti_finish{state="failed"}[5m])
    )

    # ImagePull error reason이 토글돼도 pod별 한 series로 안정화
    max by (namespace, pod) (
      kube_pod_container_status_waiting_reason{
        reason=~"ImagePullBackOff|ErrImagePull"
      }
    )
    ```

    - `by (...)`는 결과에 남길 label이고, `without (...)`은 버릴 label이다.
    - alert의 `for`는 **집계 뒤 결과 series별**로 시간을 잰다. `reason`처럼 변하는 label을 남기면 series가 갈리고 `for` 타이머가 리셋될 수 있다. [[2026-06-30 - Prometheus·Alertmanager 알림 파이프라인 메커니즘 (hermes 감지층 실측)|ImagePullBackOff 실측 교훈]].

5. **비교·논리 연산 — alert 조건은 true/false가 아니라 남는 series다**

    ```promql
    # 값이 0보다 큰 failed series만 남긴다
    airflow_ti_finish{state="failed"} > 0

    # alert가 없음을 Grafana 패널에서 0으로 표시
    sum(rate(airflow_ti_finish{state="failed"}[5m])) or vector(0)
    ```

    - 비교식은 조건을 만족하는 series를 반환하고, 만족하지 않으면 empty vector가 된다.
    - `or vector(0)`은 **표시용** 빈값을 0으로 바꾸는 패턴이다. alert에서 무심코 쓰면 "metric이 사라짐"과 "정상 0"을 구분하지 못할 수 있다.
    - `and`·`or`·`unless`는 label이 맞는 series끼리 집합 연산한다. 서로 다른 metric을 곱하거나 나눌 때는 `on(label)`·`ignoring(label)`·필요 시 `group_left`/`group_right`로 vector matching을 명시한다.

6. **Hermes에서 확인하는 순서**
    - Prometheus Graph에서 selector가 실제 series를 반환하는지 확인한다.
    - 같은 expr를 `/alerts` 또는 `Status → Rules`에서 보고 `inactive → pending → firing` 전이를 확인한다.
    - firing 뒤 Alertmanager에서 receiver·grouping·silence를 확인하고, Grafana Prometheus datasource로 시간축을 맞춘다.
    - 앱이 실제로 실행된 failure라면 Loki Explore에서 같은 namespace·pod·시각을 selector로 잡아 stdout marker·stack trace를 찾는다. [[2026-07-10 - Loki·Fluent Bit 로깅 파이프라인 (hermes 실측)#7. 디버깅·모니터링 운영 루프|Loki 조사 흐름]].
